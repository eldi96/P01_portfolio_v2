## 로컬 개발용 실행

```sh
npm ci
npm run build
npm run dev
```

Node.js 24를 사용하며 기본 로컬 주소는 http://localhost:4173 입니다. 수정 후 `npm run build`로 정적 출력을 갱신합니다.
브라우저용 Anime.js와 Three.js는 `js/vendor/`의 파일을 사용합니다.
`npm run check`는 JavaScript 문법을, `npm test`는 테스트용 Postgres에서 인증·권한 검사를 확인합니다.

## T08 패스키 개인 공간 — 구현 및 배포 준비

기존 공개 소개는 유지하고 하단에 `나만의 공간` 링크를 추가했습니다. `/private.html`은 공개된 로그인 화면이며, 비공개 기록은 인증된 `/api/passkey?action=items` 응답에만 들어갑니다.

- 프론트엔드: 기존 HTML/CSS/JavaScript + SimpleWebAuthn Browser 14.0.0.
- 서버: Vercel Node.js Function + SimpleWebAuthn Server 14.0.3. 공개키로 서명·Origin·RP ID·사용자 확인 여부를 검증합니다.
- DB: Neon PostgreSQL + pg 8.23.1. 개인키나 비밀번호는 저장하지 않습니다.
- 일회용 질문: DB에 5분 보관하고 검증 시 `DELETE RETURNING`으로 한 번만 소비합니다.
- 세션: 8시간, DB에는 임의 토큰의 SHA-256 해시만 저장합니다. HTTPS에서는 `__Host-` 접두사와 Secure/HttpOnly/SameSite=Strict 쿠키를 사용합니다. 로그아웃과 패스키 삭제 시 관련 세션을 폐기합니다.
- 최초 등록: 운영자가 발급하는 30분 일회용 초대. 등록한 뒤에는 로그인 상태에서 추가 패스키를 붙입니다. 마지막 패스키는 삭제를 막습니다.
- 계정별 가상 기록 3개를 DB에 보관하며, 요청의 계정 ID로 다른 계정에 전환하지 않습니다.

### DB 및 Vercel 설정

기존 Neon 프로젝트 `snowy-recipe-60455812`를 사용합니다. PC에서 완료한 Neon 로그인·연결을 다시 만들지 마세요. `.env.local`의 실제 값은 Git이나 노션에 올리지 않습니다.

1. 새 DB 개발 브랜치에서 먼저 검증합니다. 연결 파일에는 Neon에서 받은 `DATABASE_URL`(풀링), `DATABASE_URL_UNPOOLED`(마이그레이션용)를 둡니다. 기존 값은 유지합니다.
2. 로컬의 `APP_ORIGIN`을 `http://localhost:4173`으로 설정합니다.
3. `npm run db:migrate`로 이름이 `t08_`로 시작하는 테이블을 생성합니다. 이 명령은 등록된 마이그레이션만 한 번 적용합니다.
4. `npm run account:create -- "소유자"` 및 별도 검증 계정으로 한 번 더 실행합니다. 만들어진 `.enrollment-*.txt`는 비공개 파일이며, 그 안의 링크에서 첫 패스키를 등록합니다. 이 파일은 공유·업로드하지 말고 사용 후 삭제합니다.
5. Vercel의 기존 `p01-portfolio-v2` 프로젝트에 `DATABASE_URL`을 서버 전용 환경변수로 설정합니다. 운영 `APP_ORIGIN`은 `https://p01-portfolio-v2.vercel.app`입니다. 프리뷰에서는 별도 DB 브랜치를 사용하며 APP_ORIGIN을 따로 지정하지 않으면 Vercel이 주입한 VERCEL_URL의 정확한 Origin을 사용합니다.
6. 운영 DB 적용 전에 개발 브랜치의 검증 결과를 확인합니다. 코드 검토 후 배포하고 실제 기기에서 패스키 등록·로그인·삭제를 확인합니다. 로컬과 운영의 패스키는 서로 호환되지 않습니다.

정적 출력은 `dist/`, 서버 함수는 `api/passkey.js`입니다. `vercel.json`이 빌드·출력 경로를 지정합니다. 환경 파일·서버 소스·테스트 자료는 정적 출력에 포함되지 않습니다. Vercel의 배포 보호가 공개 페이지를 가로막지 않는지 시크릿 창에서 확인해야 합니다.

### 확인 방법과 검증 범위

1. 소개 페이지와 하단 개인 공간 링크를 엽니다. 비로그인 상태의 자료 요청은 401입니다.
2. 첫 패스키 등록 → 로그아웃 → 패스키 로그인 순서로 확인합니다. 등록 창에서 취소하면 패스키는 저장되지 않습니다.
3. 패스키 두 개를 등록하고 하나를 지웁니다. 남은 키는 로그인에 성공하고 삭제한 키는 실패해야 합니다.
4. 다른 계정의 자료 접근, 이미 쓴 질문 재사용, 로그아웃한 쿠키 재사용이 거절되는지 확인합니다.

자동 테스트는 PGlite의 실제 Postgres 엔진과 테스트용 소프트웨어 인증기의 서명을 사용합니다. 테스트용 DB가 운영 DB를 대신하지 않습니다. `test-results/passkey-api.json`에는 토큰·초대·개인키를 제외한 요청 결과가 기록됩니다. **자동 테스트 통과는 실제 Neon 접속·OS 패스키 창·Vercel 배포 검증을 의미하지 않습니다.**

### 아이폰 등 다른 기기에 추가 등록

PC의 기존 패스키로 로그인한 후 5분 이내에 ‘다른 기기 등록 링크 만들기’를 누릅니다. 링크를 본인 아이폰의 Safari에서 열고 새 패스키를 등록합니다. 아이폰에서 기존 패스키로 로그인하거나 PC와 Bluetooth로 연결할 필요가 없습니다. 같은 계정의 기록과 두 패스키가 연결됩니다.

- 추가 등록 링크는 5분 동안 한 번만 사용 가능하며 DB에는 링크 토큰의 해시만 저장합니다.
- 새 링크 발급·링크 취소·발급한 PC 세션의 로그아웃 또는 만료 시 사용할 수 없습니다. 등록 취소나 서명 검증 실패만으로는 링크를 소비하지 않으며 만료 전 다시 시도할 수 있습니다.
- 링크를 가진 사람이 새 패스키를 추가할 수 있으므로 비밀로 취급합니다. URL fragment로 전달하고 페이지를 열면 주소 표시줄에서 제거합니다. 로그·노션·공개 캡처에 넣지 않습니다.
- `002-additional-enrollment.sql`을 배포 전에 적용해야 합니다. 기존 최초 등록 초대의 동작과 기존 패스키는 보존합니다. 신규 계정을 만드는 방식이 아닙니다.
- 새 기기 등록 권한을 발급할 때에는 최근 5분 이내 로그인한 세션을 요구합니다. 일반 패스키 관리 작업의 직전 재인증은 아직 적용하지 않았습니다.

남은 제한: 모든 패스키를 잃어버린 사용자의 본인 확인 및 셀프 복구는 구현하지 않았습니다. 운영자 복구 정책을 별도로 정해야 합니다. 기존 정적 GitHub Pages 주소에서는 인증 API가 작동하지 않습니다.

검증 결과와 아직 확인하지 못한 실제 기기 항목은 [T08 검증 기록](docs/t08-verification.md)에 정리했습니다.
